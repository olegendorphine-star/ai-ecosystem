# Telegram — защищённый оператор пользовательского аккаунта

**Дата:** 09.11.2026. **Текущий статус:** код и 16 offline-тестов подготовлены; живой Telegram не подключён и не проверен. Ветку нужно принять, установить модуль на VPS, выполнить одну авторизацию владельца и затем проверить действия.

## Задача

Из обычного чата ChatGPT управлять **собственным Telegram** без постоянно включённого ПК: проверка авторизации, список диалогов, чтение сообщений и ответы на существующие входящие обращения. Telegram Mini Apps (включая Connect) требуют **дополнительного браузерного исполнителя** — MTProto не заменяет интерфейс Mini App.

## Изоляция и безопасность

Публичный GitHub хранит **только код и шифротексты**. Никогда не размещать в issue / workflow log телефон, API id/hash, код входа, 2FA, файлы сессии, имена и сообщения клиентов, приватные ключи. Сессия и ключи сохраняются на VPS в каталоге ~/.telegram-agent с правами 0700/0600. GitHub workflow принимает команды исключительно от владельца olegendorphine-star через отдельный [Issue #119](https://github.com/olegendorphine-star/ai-ecosystem/issues/119).

Маршрут: ChatGPT → X25519/HKDF/AES-GCM шифрование → owner-only issue comment → GitHub Actions по pin SSH → VPS/Telethon → зашифрованный ответ → ChatGPT. Для каждой команды UUID, TTL до 10 минут, одноразовый ключ ответа. Серверные ключи не отправляются в ChatGPT. В публичном issue не должно быть незашифрованных команд и ответов.

Поддержаны только действия status, dialogs, read, reply. Команда reply требует конкретную входящую реплику, текст и approved_by_owner=true. SQLite хранит идентификатор команды и устойчивый Telegram random_id: повторы не должны порождать дополнительную отправку. Массовые холодные сообщения, обход защит, оплаты и удаление запрещены.

## Установка (после review и merge PR)

1. Выполнить вручную GitHub Actions **Telegram owner — private VPS deployment**. Он загружает только Python-файлы на существующий VPS и создаёт отдельное виртуальное окружение. Никакие Telegram-учётные данные workflow не получает.
2. На VPS создать серверную пару ключей: `~/.telegram-agent/venv/bin/python ~/.telegram-agent/app/tools/telegram_secure_bridge.py init-key`. Сохранять публичный ключ (строку base64), закрытый ключ остаётся на VPS. Повторный init-key блокируется.
3. В приватном терминале владельца создать файл `~/.telegram-agent/private/telegram.env` с `TELEGRAM_API_ID=<...>` и `TELEGRAM_API_HASH=<...>` из https://my.telegram.org. Права файла 0600, папки 0700. Пароли и коды входа не публиковать.
4. В защищённом **интерактивном** терминале VPS, без GitHub Actions логов: `set -a; . ~/.telegram-agent/private/telegram.env; set +a; ~/.telegram-agent/venv/bin/python ~/.telegram-agent/app/tools/telegram_owner_operator.py --login`. Код и пароль 2FA вводит только владелец. Секреты и сессия не передаются ассистенту.
5. После входа выполнить через шифрованный issue-канал команды status, dialogs, read. Только после согласования конкретного ответа — тестовый reply. Проверить фактическую доставку в официальном приложении, затем повторить после перезапуска VPS.

## Ограничения и критерии приёмки

Нет развертывания production или доступа к Telegram, пока ручной deploy и вход не выполнены. Успех offline-тестов / GitHub Actions сам по себе **не доказывает** авторизации. Нужны: прямое подтверждение Telegram API, чтение реального диалога по encrypted bridge, один разрешённый ответ в действующем диалоге, повторная работа после перезапуска. Полностью автономные ответы 24/7, поиск вакансий и отклики через Telegram Mini Apps — отдельные расширения после базовой приёмки.

Архив и документация коммерческого проекта сохраняются в Google Drive отдельно от Gii. Внешняя память содержит только архитектуру и обезличенные статусы, не тексты клиентов.
