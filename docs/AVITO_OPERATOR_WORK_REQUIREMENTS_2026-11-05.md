# ТЗ: оператор Авито для проекта «Персональная ИИ-экосистема»

Статус: требования заказчика, 05.11.2026. **Не считать реализованным**. Репозиторий и GitHub Secrets уже подключены; повторно получать ключи без причины не нужно. Не относится к Gii.

## Цель и критерий готовности

ChatGPT Work + GitHub Actions + Avito API должны выполнять **реальные изменения в аккаунте Авито**, а не только читать данные или выдавать HTTP 200. Для каждого действия: предварительное состояние → разрешённая операция → подтверждённое состояние в Авито → журнал без секретов/персональных данных. При ошибке не утверждать успех.

## A. Публичный профиль / профили (приоритет P0)

1. Инвентаризовать фактические доступные поля профиля в интерфейсе и документированные API-права: название, описание, логотип/фотография, обложка, сфера деятельности, контакты, часы работы и прочие **только реально доступные** поля.
2. Заполнять пустые и изменять существующие поля по утверждённым материалам проекта, не заменяя содержимое без одобрения владельца.
3. Если официальный API не поддерживает редактирование, использовать авторизованный браузер ChatGPT Work после проверки допустимости и доступности этих действий.
4. До/после: читать обновлённое значение в интерфейсе/документированном API. Не обходить капчу или ограничения безопасности.

Приёмка: хотя бы одно согласованное поле реального публичного профиля изменено и изменение видно после перезагрузки; отдельный список редактируемых и недоступных полей.

## B. Объявления (приоритет P0)

1. Создавать объявления в поддерживаемых категориях, особенно в «Услугах», на базе утверждённого текста и 6 изображений проекта.
2. Редактировать заголовок, описание, стоимость, категорию (если Авито позволяет), характеристики, фото и остальные фактически редактируемые поля.
3. Работать с уже существующими объявлениями и черновиками; до обновления установить идентификатор в Авито и идентификатор источника автозагрузки, чтобы исключить дубль.
4. Публиковать, проверять модерацию, уведомлять о блокировке и реальном статусе.
5. Снимать с публикации/архивировать **без удаления**; отдельная функция восстановления, если доступна.
6. Способ исполнения: предпочесть официальное API/автозагрузку после проверки допустимой схемы изменения и снятия; при отсутствии поддерживаемой команды использовать Work через интерфейс сайта, с проверкой результата.
7. Не использовать `POST /core/v1/items/{item_id}/update_price` для категории «Услуги»: по изученной спецификации метод ограничен другими категориями.
8. Не отправлять `POST /autoload/v1/upload` до верификации состава фида: метод может немедленно опубликовать или активировать объявления.

Приёмка: один согласованный тест изменения существующего объявления с проверкой; затем согласованные тесты публикации нового, снятия и повторного включения. Каждый тест не должен создавать дубликатов или незапланированных расходов.

Контрольные объекты: активное объявление №8347570435; черновик №449877076 (существование в UI подтверждено владельцем, доступ через пробованные API не получен). Эти номера не взаимозаменяемы.

## C. Каталог платных услуг продвижения (приоритет P0)

Для каждого нашего объявления сформировать **реальную персональную витрину**, не общие примеры из документации:
- наименование и `slug` услуги;
- подходит ли для конкретного объявления/категории;
- точная цена с валютой и единицей тарификации, срок действия;
- текущий статус, дата окончания, повторные списания (если применимо);
- лимиты, особенности, основания недоступности;
- возможный метод включения и метод проверки исполнения/остановки.

Первичные источники: `POST /core/v1/accounts/{userId}/vas/prices` (прайс и доступные услуги), `POST /promotion/v2/items/services/get` (действующие услуги), `POST /promotion/v1/items/services/bbip/suggests/get` (бюджетные предложения), документированные способы цены/заказа. Получить конкретные значения, не ограничиваться HTTP 200.

Приёмка: реальная таблица доступных услуг для №8347570435; отдельная таблица уже подключённых услуг, с явным указанием «нет» или «не удалось установить».

## D. Покупка, ставки, бюджеты, остановка продвижения (приоритет P1)

1. С включением только после явного согласия владельца по конкретной услуге, стоимости, сроку, лимиту и объекту: API `PUT /core/v2/items/{itemId}/vas/` или применимый BBIP-механизм.
2. После команды проверять идентификатор заказа, итоговый статус операции, фактическое применение услуги, фактические/ожидаемые расходы; учитывать задержку и частичные ошибки.
3. Для поддерживаемого аукциона: `GET /auction/1/bids` → предложить разрешённую ставку → с одобрением `POST /auction/1/bids` → перепроверить.
4. Для поддерживаемого CPX: `GET /cpxpromo/1/getBids/{itemId}` → `POST /cpxpromo/1/setManual` или `setAuto` → проверка; `POST /cpxpromo/1/remove` только если относится к активному продвижению и пользователь разрешил остановку.
5. Отдельный Avito Ads (кампании/группы/креативы) не путать с продвижением объявлений; подтвердить права аккаунта/токена до обещаний управления.
6. Никаких автоматических платных операций, изменения ставок, бюджетов или перераспределения средств без утверждённых владельцем правил. Дневной и суммарный предел расходов; проверять баланс и доступные средства. Не делать повторную платную заявку при сетевой ошибке до проверки исходного заказа.

Приёмка: под разрешением владельца успешное подключение одной доступной услуги и успешное считывание её статуса; отдельно проверенные изменение и остановка соответствующего режима продвижения, если аккаунт поддерживает.

## E. Техническая реализация

- GitHub: отдельные ветки и draft PR, mock-тесты, type-checked request schemas, timeout, retry с учётом rate-limit, идемпотентность, хранение секретов исключительно в GitHub Secrets.
- Раздельные действия `inspect`, `prepare`, `execute`, `verify`; методы записи не должны запускаться от обычного `push`.
- Для каждой write-операции требовать одноразовый проверяемый план с точными `itemId`, параметрами, ожидаемой стоимостью, подтверждением владельца и тестом после выполнения.
- Browser Work как резервный исполнитель для действий, которые API реально не покрывает. Отдельный список ограничений браузера и возможных ручных подтверждений.
- Не читать и не отправлять клиентские сообщения: пользователь ведёт переписку сам.
- Google Drive: хранить утверждённые материалы, паспорт интеграции, результаты приёмки и решения; синхронизировать после существенных изменений.
- Не смешивать разработку и тестирование с проектом Gii.

## Порядок работ и стоп-факторы

0. Без изменения Avito аккаунта: точный перечень API-схем, scopes и доступов; каталог платных услуг с ценами; полное сопоставление активных услуг.
1. Через Work проверить UI-права профиля и старого черновика, без изменения.
2. Реализовать операторские действия с guardrails, тестами и журналом проверки.
3. Первое изменение реального объявления/профиля — только по согласованному изменению.
4. Перейти к публикации/снятию, затем платному продвижению и ставкам.

**Главный критерий:** в итоговом отчёте отдельно перечислить «реально исполнено и проверено», «метод найден, но не проверен», «невозможно/нет доступа». Нельзя объявлять готовность на основании существования метода API.
