# Авито: безопасный отчёт о профиле без скриншотов GitHub Actions

Дата: 05.11.2026. Владелец поставил целью управлять всем профилем и объявлениями через уже настроенный API, **без работы с перепиской**.

## Проблема

GitHub connector успешно читает файлы, PR и задания по известному run_id, но не даёт напрямую перечислить push-triggered workflow runs. Поэтому даже выполненная живая диагностика профиля становится недоступной для чтения из чата без присланной пользователем ссылки или скриншота.

## Реализация

Отдельный workflow `.github/workflows/avito-profile-report-once.yml` проводит строго ограниченную **read-only** проверку профиля через `tools/avito_profile_inventory.py`. Сырой ответ хранится только во временном файле GitHub runner, не публикуется в логах и удаляется после обработки. Новый `tools/avito_profile_report_guard.py` отбирает только HTTP-коды, булевы статусы, счётчики и заранее разрешённые имена полей категории. Только проверенный JSON сохраняется в `docs/reports/avito-profile-inventory-2026-11-05.json`. Эту единственную запись GitHub сможет читать без номера Actions run.

Приватные имена, контакты, userId, URL рабочего фида, секреты, сообщения клиентов и содержимое профиля **никогда не записываются** в отчёт. Живой запуск допускается только из main после офлайн-тестов; однократно 05.11.2026 при точном заголовке merge-коммита `RUN_ONCE_AVITO_REDACTED_REPORT_PR19_2026_11_05`, либо вручную `workflow_dispatch` с флагом `approve_readonly=true`. Для записи отчёта GitHub Actions использует `GITHUB_TOKEN` с `contents:write` только в job записи, не ключи Avito. Новый GitHub-отчёт не содержит никаких Avito write-методов.

## Обязательные контрольные пункты

1. Перед merge: CI проверяет восемь тестов `test_avito_profile_report_guard.py` и восемь тестов `test_avito_profile_inventory.py`.
2. В PR доступны только тесты. Job `publish_redacted` на PR должен быть **skipped**.
3. После разрешённого merge в main: запускается однократный live job; он вправе только читать Avito API. Никаких сообщений, публикаций, покупок, изменения баланса или профиля.
4. Даже успешное завершение workflow не доказывает доступности поля PriceList; проверять значения HTTP category_tree/category_fields и `pricelist_observed_in_fields` в JSON после проверки конкретной категории.
5. При отказе GitHub push, HTTP 429 или отсутствии категории не интерпретировать это как подтверждённую доступность всех полей. Диагностировать отдельно, без массовых повторных запросов.
6. Отдельно контролировать закрытый PR #18 и неслятый PR #16 с неподтверждённым PriceList. Живой XML `docs/avito-feed.xml` не трогать.

## Границы

Это мост для **наблюдения**, а не завершение «полного управления» аккаунтом. Следом нужен реестр разрешённых операций записи по профилю и объявлениям, схема PriceList по официальному шаблону и отдельное безопасное выполнение каждого обновления. Для UI-only настроек останется браузерный доступ.
